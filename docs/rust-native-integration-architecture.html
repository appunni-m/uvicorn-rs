Architecture status · 12 October 2026

Native uvicorn-rs with a thin Python compatibility client

Ship two modes side by side: uvicorn-rs is the Rust server/library, and uvicorn-rs-py is its separate thin client for Python ASGI applications. Rust applications compose fastapi-rs over starlette-rs directly, with one typed Rust request path from the server through the handler and back.

Package names and language boundary

uvicorn-rs itself is the native server; there is no separate uvicorn-rs-native product. uvicorn-rs-py is a distinct Python compatibility client that can be installed and used alongside the native package. This is a greenfield package layout: the former Python distribution, import path, Cargo shape, and CLI are not compatibility constraints. Standard Python ASGI apps still execute in Python and cross the ASGI bridge; the Rust-native FastAPI-RS/Starlette-RS path has no Python request boundary.

01 · Today

Current architecture: Rust owns the wire, Python owns the ASGI application

The target package split is already explicit: uvicorn-rs is the Rust-native server, while uvicorn-rs-py is the Python ASGI compatibility client. In the current implementation, the Python extension still contains an overlapping network stack and does not call the native crate, so the client is not yet thin. The migration consolidates protocol ownership in uvicorn-rs; uvicorn-rs-py then owns Python app loading, asyncio/PyO3 bridging, and ASGI adaptation.

Request direction runs left to right. The response and each body/message event travel back through the same Rust–Python bridge.

02 · Target

Rust-native architecture: a direct service call, no Python request path

uvicorn-rs is the single native server package and accepts Rust services; it is not a native variant alongside another Rust server package. FastAPI-RS composes Starlette-RS as its Rust framework layer and passes the resulting service to Uvicorn-RS. The separate uvicorn-rs-py, starlette-rs-py, and fastapi-rs-py clients bridge Python integrations and supported upstream-version differences. The current 36-case native contract matrix passes three times (108/108); the H2 reset and H1 peer write-half-close inputs provide generic request and connection lifetime observations, not ASGI disconnect semantics. An archived 17-case FastAPI-native H1/H2 receipt belongs to an earlier dirty sibling snapshot; its example currently references a missing sibling crate and is not reproducible from the checked-out sources. Native transport integration into uvicorn-rs-py, composed H3/TLS, pinned sources, Python FastAPI parity, WebSocket sessions, framework lifecycle integration, and performance remain open.

FastAPI-RS builds on Starlette-RS; Uvicorn-RS hosts the composed Rust service.

FastAPI-RS uses Starlette-RS by default. A Rust application can depend directly on both the framework and server; FastAPI-RS may also expose an opt-in Cargo feature for Uvicorn-RS. Starlette-RS remains server-neutral and does not depend on or bundle Uvicorn-RS.

uvicorn-rs is native; uvicorn-rs-py uses it for Python ASGI hosting.

The native server and Rust framework crates have no PyO3 or Python runtime dependency. The planned uvicorn-rs-py integration uses the native transport while keeping Python app loading, event-loop ownership, and ASGI conversion in the thin client; that connection is not implemented yet. fastapi-rs-py and starlette-rs-py provide corresponding Python compatibility surfaces. Each client publishes tested version combinations for the Python packages it integrates with; these are separate compatibility profiles and do not promise full Uvicorn CLI/API compatibility. The Python clients are separate installable packages and stay out of the Rust-native dependency graph. A Python ASGI callable still runs in Python and uses the GIL where required.

In the all-Rust case, the request stays in Rust from socket acceptance through the handler and back to the socket. Response bodies remain streams, so demand and cancellation can propagate directly.

Python ASGI client: uvicorn-rs-py

This thin client loads module:app, preserves the app's owning asyncio loop, and adapts ASGI calls to the native server service. Standard Python FastAPI/Starlette apps still cross Python for ASGI callbacks; that path uses the GIL as required.

Framework clients: fastapi-rs-py and starlette-rs-py

These optional clients hold Python object conversion and upstream-package version shims. Their compatibility matrix is separate from the native Rust framework APIs and they are not linked into the all-Rust request path.

Where the native request handoff happens

Uvicorn-RS calls the FastAPI-RS service once per request with a Rust request and body stream. FastAPI-RS then calls Starlette-RS routing, middleware, validation, and the Rust handler as ordinary Rust code. “Once” describes the server-to-service call; it does not describe one Python callback. A Python handler or standard ASGI callable still crosses into Python and uses the GIL.

03 · Dependency direction

Keep frameworks cohesive and the network runtime replaceable

The useful cohesion is shared Rust request/response semantics and native composition. It does not require Starlette-RS to depend on or bundle Uvicorn-RS. A framework should still be usable in tests, a different server, or an embedded host.

FastAPI-RS native core

Routes, dependencies, validation, serialization, and OpenAPI. It uses Starlette-RS primitives and has no PyO3 dependency in the target graph.

Starlette-RS core

Reusable web toolkit: middleware, request/response, routing, WebSocket, lifespan, and streaming. Keep it server-neutral and free of Python bindings.

Thin Python compatibility clients

fastapi-rs-py, starlette-rs-py, and uvicorn-rs-py own Python loading/conversion and any version-specific glue for supported Python package releases. They stay outside the native Rust dependency graph.

Generic Rust service contract

Prefer established http, http-body, and Tower Service interfaces. Add a small neutral extension only for WebSocket sessions or lifecycle semantics they do not express.

uvicorn-rs native server

Consumes the generic service; owns listeners, HTTP/1.1, HTTP/2, HTTP/3, TLS/QUIC, WebSocket transport, backpressure, cancellation, and shutdown. No PyO3 dependency.

uvicorn-rs-py ASGI adapter

Depends on the native server plus a thin asyncio/PyO3 bridge. It hosts standard Python ASGI apps and keeps callbacks on the application-owned Python event loop.

Optional native integration

An application binary or a small fastapi-rs-uvicorn crate composes the Rust service with the Rust server. The server never imports framework internals.

Recommended ownership: FastAPI-RS depends on Starlette-RS as its default Rust framework layer. Starlette-RS depends on reusable HTTP/service primitives, never on Uvicorn-RS. The native uvicorn-rs server consumes those primitives and never imports framework internals. A Rust application composes FastAPI-RS with Uvicorn-RS directly; FastAPI-RS may offer a disabled-by-default server feature. The *-py clients own Python compatibility and remain absent from native binaries.

Where should the optional Uvicorn-RS integration live?

Direct Rust dependency with an optional FastAPI-RS feature User-approved option

FastAPI-RS can depend optionally on the native uvicorn-rs crate and expose a feature such as server-uvicorn for serve(app). Keep the feature disabled by default. A standalone application can also depend on FastAPI-RS and Uvicorn-RS directly.

Why: direct Rust-level integration is cohesive while the default FastAPI-RS and Starlette-RS graph remains usable without the server.

Optional Cargo feature on FastAPI-RS

The optional Cargo dependency is the Rust-native integration. It may re-export a convenience runner without pulling in PyO3 or any Python compatibility client.

Cost: feature combinations and semver/MSRV coordination move into FastAPI-RS CI and release policy. Keep it disabled by default and do not let Starlette-RS inherit it.

Application binary composes both directly

A Rust application depends on FastAPI-RS and Uvicorn-RS and passes its router/service into the server. This has the fewest hidden dependencies and is the clearest first native prototype.

Cost: each app owns a small amount of bootstrap code until an optional integration crate exists.

How do Python extras differ from native server features?

A Cargo feature on native fastapi-rs may enable its optional Rust dependency on uvicorn-rs. A Python extra on fastapi-rs-py may install uvicorn-rs-py and other Python distributions; it does not itself enable a Cargo feature or remove Python from that process. Exact Python extra names remain a packaging decision.

Keep the controls distinct: Rust applications link fastapi-rs, starlette-rs, and uvicorn-rs without Python clients. Python applications use the *-py clients and cross the Python boundary. Any extra intended to ship a native binary must explicitly package that binary and document that it is a separate execution mode.

04 · Rust boundary

Define the seam around streams and connection lifetime

A request/response type alone is not enough for this server. The boundary must carry streaming bodies, WebSocket sessions, cancellation, lifespan, and connection metadata without recreating ASGI’s Python message loop.

HTTP request and response

The prototype dispatches http::Request<hyper::body::Incoming> through Tower Service and accepts a response body implementing http_body::Body<Data = Bytes>. Starlette-RS's local NativeApplication implements its service over generic request bodies and erases heterogeneous response bodies to UnsyncBoxBody at its route boundary. Its prebuilt-response fallback copies bytes from Vec<u8>; native owned Bytes frames pass through without collection. Sharing http types alone does not make parsing, TLS, or serialization zero-copy. The cross-repository bounds remain provisional.

Body streaming and backpressure

Use a frame/body trait such as http_body::Body. Polling and bounded capacity must reflect downstream demand; dropping a body or request must cancel its owned work.

WebSocket session

Expose a typed session with text, binary, close code/reason, negotiated subprotocol, and stream-scoped cancellation. The transport handles RFC 6455 Upgrade for H1 and Extended CONNECT for H2/H3; its adapter owns framing and Ping/Pong.

Lifespan and graceful shutdown

Startup runs before accepting requests. Shutdown stops accepting, drains requests and sessions to the deadline, cancels and joins remaining work, then runs the application shutdown hook within the remaining budget.

Context and observability

Pass peer address, TLS/protocol metadata, request ID, extensions, tracing span, and cancellation token as Rust values. Rust does not implicitly inherit Python contextvars.

Errors and response commitment

Use typed Rust Result errors. Before headers commit, map an application failure to an HTTP error response; after commit, terminate/reset the stream and preserve the original cause for diagnostics.

Grow the first live contract into a tested vertical slice

The generic Tower service now has a 36-case real-socket contract over cleartext H1/H2, TLS H1/H2, H3, and native lifecycle hooks, passed three sequential local repeats (108/108). The added H2 reset case observes ServiceFutureDropped while confirming the connection remains usable; it does not determine the cause or establish ASGI http.disconnect. The H1 case completes a held response after client write-side shutdown while the connection lifetime remains open, consistent with RFC 9112 §9.6. Seven inputs cover startup state, drain ordering, typed hook errors, and timeout cancellation. H3 cases verify QUIC metadata, streamed request and response frames, trailers, first data before app completion, finite slow-reader backpressure with producer cancellation, and graceful drain. This evidence is isolated to the core: the local composed Starlette/FastAPI examples still use H1/H2, and the H3 API expects the caller to configure Quinn and TLS. These cases do not claim full RFC 9114 conformance. Keep errors as Rust Result values. This branch does not serialize native requests into ASGI dictionaries.

Keep the first contract small. Pin the http, http-body, and Tower versions in a shared workspace policy or compatible release range. Avoid a Uvicorn-named type dependency in Starlette-RS. ADR 0004 records a tiny runtime-neutral contract crate. Its lifecycle hooks are implemented provisionally in the core and are not API-stable; WebSocket sessions remain proposed.

05 · Boundary truth

“One last application-layer crossing” is only possible for a narrower Python API

A Python ASGI callable may await many times, receive multiple upload chunks, send streamed response chunks, accept or close a WebSocket, and run lifespan events. Those operations are separate interactions with its Python event loop. A Rust server cannot turn them into one FFI call and still preserve general ASGI behavior.

For a Python endpoint that accepts one fully buffered request and returns one fully buffered response, a dedicated synchronous or coarse-grained RPC-style adapter could cross once per request. That is a different contract: it changes streaming, cancellation, WebSocket, and async semantics, and it still uses the GIL while Python code runs.

The robust zero-boundary condition

The server, framework, route handlers, dependencies, validators, serializers, middleware, and relevant app state must all remain Rust-native for the full request lifecycle. A single Python callback reintroduces interpreter work and the GIL for that callback.

Python model definitions and Pydantic

FastAPI-RS currently documents Pydantic’s public model API as a compatibility requirement and Pydantic v2’s Rust pydantic-core as the validation/serialization engine. Rust validation can reduce Python execution, but Python class construction, custom validators/serializers, Python callbacks, and Python model objects remain boundary work. Decide whether the native Rust API uses Rust model types, accepts a Python model as an explicit compatibility bridge, or supports both modes with a clear cost.

Keep this distinction visible in benchmarks: “Rust transport + Python route” measures the compatibility stack, while “Rust transport + Rust FastAPI-RS/Starlette-RS route” measures the no-Python path.

06 · Python boundary profiles

Choose whether Python is a compatibility path, a leaf callback, or absent

“One interaction at the application layer” can describe a coarse Python handler call, a one-time Python bootstrap, or a Rust-only request path. They have different runtime guarantees. Keep them as explicit modes instead of describing all three as Python-free.

The strict goal has no Python application call.

A Python leaf callback can reduce the number of crossings for a custom hybrid API, but it still enters Python and acquires the GIL. To remove Python and the GIL from the process, use Rust handlers in a Rust binary. To keep Python involved only during setup, construct a Rust service once and ensure it holds no Python-owned state on its request path.

Target Python compatibility mode

Python ASGI application

Rust transport→ uvicorn-rs-py adapter↔ asyncio / uvloop→ Python ASGI callable

uvicorn-rs-py module:app supports standard Python ASGI applications. Scope creation, callable invocation, every awaited receive()/send() operation, messages, cancellation, and exceptions use the Python bridge. The Python loop owns app tasks and context. Its matrix declares Python/runtime and ASGI support, plus exact upstream Uvicorn versions only for integrations the client actually implements. Accepting module:app does not imply full Uvicorn CLI/API compatibility.

Guarantee: Python and the GIL are required for Python code. The old uvicorn-rs import and CLI layout is not part of this compatibility promise.

Optional migration mode

Rust pipeline with a Python leaf handler

Rust server→ Rust routing / middleware→ Python handler call→ Rust response path

A separate typed endpoint adapter could call a Python handler once at the route leaf for a simple request/response API. It is not standard ASGI. Python code still runs under the GIL; an async def handler still needs the Python event loop and may require scheduler handoffs across awaits. Streaming, disconnect cancellation, WebSockets, lifespan, Python context, and Python exceptions need explicit contracts.

Guarantee: fewer boundary calls may be possible for selected synchronous handlers, but neither “one FFI transition” nor zero-GIL execution is guaranteed. Treat this as an opt-in migration adapter and benchmark it separately.

Proposed embedded mode

Python bootstraps a Rust-native service

Python configuration→ one setup Rust service handle→ Rust server + Rust handlers

A Python package could construct/register Rust route state at startup and hand a Python-free service handle to the Rust server. Requests then stay in Tokio and the Rust framework pipeline; do not retain Python callables, objects, or loop-bound state in handlers, middleware, validators, or response bodies.

Guarantee: no Python work on the request path if the service graph is truly Python-free. Because the host is Python, the interpreter and GIL still exist in the process. Startup/shutdown hosting and cancellation semantics need a prototype.

Target for zero Python runtime

Standalone Rust-native process

Rust binary→ uvicorn-rs native server→ FastAPI-RS → Starlette-RS→ Rust handler

The binary links native uvicorn-rs and Python-free FastAPI-RS/Starlette-RS crates. Typed requests, streaming bodies, middleware, routing, validation, serialization, WebSockets, cancellation, and shutdown remain Rust values and futures end to end.

Guarantee: no Python interpreter, Python event loop, PyO3 dependency, or GIL in the process. A Python ASGI application is not accepted in this mode.

Python compatibilityDoes uvicorn-rs-py pass the declared ASGI cases for each supported Python/runtime profile and exact upstream Uvicorn integration versions? Do the framework clients pass their own tested version combinations?Publish separate version matrices for the server and framework clients; list Uvicorn CLI/API compatibility only when explicit cases establish it, and do not infer all cross-version combinations. Keep Python event-loop, context, error, streaming, and cancellation behavior in the adapter contract. The former uvicorn-rs import/CLI is not a compatibility gate.
Package graphCan Starlette-RS compile and run without Uvicorn-RS? Can FastAPI-RS compile without the optional server feature?Require both answers to be yes for the default dependency graph.
No-Python buildDoes the Rust binary dependency tree contain PyO3, a Python binding crate, or a Python runtime dependency?Require none in the standalone Rust server/framework path; keep them behind Python adapter packages.
PerformanceDoes the all-Rust path reduce per-request CPU and latency with representative FastAPI-RS workloads, while staying correct under streaming and slow readers?Publish results by workload and mode; do not infer a speedup from Rust transport alone.

08 · Architecture rules

Keep these boundaries stable as the implementation grows

Server owns transport

Uvicorn-RS owns sockets, protocol state, TLS/QUIC, flow control, transport cancellation, and graceful shutdown.

Starlette owns portable web primitives

Starlette-RS owns reusable application-level behavior and never requires one particular server.

FastAPI owns higher-level API behavior

FastAPI-RS composes Starlette-RS at the Rust API level instead of duplicating a second web runtime.

Python is an explicit compatibility mode

The *_py clients are intended to stay thin and isolated; the current uvicorn-rs-py still duplicates transport until migration. Python mode keeps the event loop, GIL, and ASGI semantics.

Do not serialize native calls as ASGI dictionaries

Rust-native routes use typed request, response, body, and session values from the server to the handler.

Compose; do not bundle

Applications select and link the server. Framework crates remain independently testable and portable.
